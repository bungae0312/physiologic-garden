# 검색 시스템 설계

## 0. 출발점

아키텍처 문서에서 이미 "클라이언트 인메모리 검색(서버 없음)"으로 결정. 이번 설계는 이 프로젝트만의 진짜 어려운 문제 — **한글/영문 혼용 + 임상 전문용어 + 장기 확장성**을 실제로 풀어낸다.

---

## 1. 라이브러리 추천

| 라이브러리 | 장점 | 단점 | 적합도 |
|---|---|---|---|
| **Orama** | TypeScript 네이티브, 커스텀 토크나이저 자유도, **키워드+벡터 하이브리드 검색 기본 지원**, 정적 문서 검색 용도로 설계됨 | 신생이라 생태계 자료가 적음 | ★★★★★ 추천 |
| MiniSearch | 검증된 안정성, 초경량(~9KB), 문서화 풍부 | 순수 키워드만 — 벡터 검색은 별도 레이어 필요 | ★★★★ 안전한 대안 |
| FlexSearch | 가장 빠름, CJK 토크나이저 프리셋 내장 | 다중 필드·TS DX가 거칠고 문서화 부족 | ★★★ |
| Fuse.js | API 가장 쉬움 | 배열 전수조사 방식 — 노트 수백 개 넘으면 랭킹/속도 무너짐 | ★★ 부적합 |

**Orama 추천 이유**: 아키텍처 문서 10번(AI 확장)에서 "검색 엔진을 통째로 교체하지 않고 그 위에 벡터 검색을 얹기만 하면 되도록" 설계하라는 원칙을 이미 세웠다. Orama는 키워드+벡터를 같은 인덱스·API에서 하이브리드로 지원하도록 설계됐다. 실제 구현 단계에서 한글 토크나이저 커스터마이징이 번거로우면, `lib/search/` 어댑터 경계 덕분에 MiniSearch로 교체 비용은 낮게 유지된다.

## 2. 검색 범위 재정의: 6개 필드 + 동의어 문제

**진짜 새로운 필드**

| 필드 | 원본 |
|---|---|
| title | frontmatter |
| tags | frontmatter |
| headings | 본문 헤딩(TOC 데이터 재사용) |
| body | 본문 plain text |
| category | 파일 경로 |
| references(논문명) | frontmatter — Article 페이지의 Reference 데이터 재사용 |

**필드가 아니라 "용어 매칭" 문제**: 근육명(대퇴사두근)·질환명(회전근개파열)은 별도 필드가 아니라 이미 `body`/`tags` 안의 도메인 용어다. 검색이 안 되는 진짜 원인은 필드 부족이 아니라 ① 한글 조사로 토큰이 깨지는 문제, ② 약어/한글/영문이 다른 문자열로 취급되는 문제(ACL ≠ 전방십자인대) — 3, 4번에서 직접 해결한다.

---

## 3. 한글 · 영문 토크나이징 전략

**영문**: 공백/구두점 토크나이징 + 소문자 정규화 + 어형 변화 흡수 — 라이브러리 기본 기능으로 충분.

**한글 하이브리드 전략** (빌드 타임, Node 환경에서 1회 수행):

```
본문 텍스트
   → [1차] 형태소 분석 기반 정규화(조사 제거, 어간 추출)
   → [2차] 정규화된 토큰을 2~3글자 n-gram으로 재분할
   → 인덱스 저장
```

형태소 분석이 실패해도 n-gram이 부분 매칭을 보장하는 이중 안전망.

**혼용 처리**: "ACL 재활 프로토콜"처럼 한 문장에 한글·영문이 섞이면 커스텀 토크나이저가 한글 구간/라틴 구간의 경계를 감지해 각각의 전략으로 나눠 처리 후 병합. 이 로직은 어떤 라이브러리를 쓰든 직접 설계해야 하므로, 라이브러리 선택 기준은 "한글 기본 지원 여부"가 아니라 "커스텀 토크나이저를 얼마나 자유롭게 꽂을 수 있는가".

**한글 fuzzy의 함정**: 한글 음절은 자모 2~3개가 합쳐진 한 글자라 일반 fuzzy(edit-distance)를 그대로 적용하면 이상하게 동작. 영문 토큰에는 라이브러리 fuzzy를 적용하고, 한글 토큰의 오탈자 허용은 n-gram 부분 일치 자체가 담당하도록 분리.

## 4. 동의어/별칭 사전 — 기존 자산 재사용

`_meta/tags.yaml`의 태그 별칭(ACL ↔ 전방십자인대)을 검색 전용 동의어 사전으로도 재사용 — 새 파일을 만들지 않음.

동작 방식은 **인덱스 확장이 아니라 쿼리 확장**:

```
사용자가 "ACL" 입력
   → 동의어 사전 조회 → ["ACL", "전방십자인대", "전십자인대"]
   → 세 단어를 모두 질의해 결과 병합·중복제거
```

taxonomy 관리(tags.yaml 정리)와 검색 정확도가 같은 데이터를 공유 — 저자가 태그를 정리할 때마다 검색도 함께 좋아짐.

---

## 5. 검색 정확도 — 필드 가중치

| 필드 | 가중치 | 이유 |
|---|---|---|
| title | 최상위 | 가장 신뢰도 높은 신호 |
| tags | 상위 | 저자가 명시적으로 분류 |
| headings | 중상위 | 구조적으로 강조된 위치 |
| references(논문명) | 중(정확 일치시 상향) | 정확한 문헌명 검색은 title급으로 |
| body | 하위 | 언급 빈도는 높지만 신호는 약함 |

prefix 매칭 필수 — "전방십"만 쳐도 즉시 매칭돼야 함(치는 도중 결과가 보이는 경험).

---

## 6. 검색 속도

- 네트워크 지연 원천 없음(클라이언트 인메모리) — 어떤 라이브러리를 골라도 공짜로 따라오는 이점
- 인덱스+라이브러리는 Ctrl+K 첫 오픈 시에만 동적 로드
- 디바운스 불필요 — 인메모리 쿼리는 즉시 반환되므로 키 입력마다 재검색해도 됨
- **장기 확장 대비(측정 후 도입)**: 인덱스가 실제로 무거워지면 "경량 인덱스"(title/tags/headings, 즉시 로드)와 "전체 본문 인덱스"(body, 백그라운드 추가 로드)로 분리. 지금 미리 만들지 않음.

## 7. Ctrl+K 인터랙션 플로우

```
┌──────────────────────────────────────────────┐
│ 🔍  acl 재활                              Esc │
├──────────────────────────────────────────────┤
│ 노트                                          │
│  ● 전방십자인대손상 재활 프로토콜                  │
│    물리치료 › 무릎 · "...[ACL] 재건술 후 12주..." │
│  ● 스포츠손상 복귀 기준                          │
│    물리치료 › 무릎 · 태그: #ACL #복귀기준         │
├──────────────────────────────────────────────┤
│ 태그                                          │
│  #ACL (14개 노트)                              │
├──────────────────────────────────────────────┤
│ ↑↓ 이동   ↵ 열기   Esc 닫기                    │
└──────────────────────────────────────────────┘
```

빈 입력 상태(타이핑 전)엔 "최근 업데이트된 노트" + "내가 최근에 열어본 노트"(localStorage, 즐겨찾기와 동일한 패턴)를 미리 표시. 결과는 매칭어 하이라이트, 전체 키보드 조작(↑↓/Enter/Esc).

## 8. 파이프라인상의 위치

MDX 파이프라인의 **Phase 2(컬렉션 전역 집계)**에서 검색 인덱스가 조립됨 — 태그 인덱스·백링크 그래프와 같은 자리. 별도 빌드 단계 불필요.

---

## 9. 향후 확장: 벡터/하이브리드 검색

- `references` 필드는 이미 구조화돼 AI가 근거로 인용 가능
- 동의어 사전은 AI 자동 태깅 시 라벨 후보로 재사용
- Orama 선택 시 노트 임베딩이 생기는 시점에 같은 인덱스에 벡터 필드만 추가 — 검색 엔진 교체·UI 재설계 불필요
